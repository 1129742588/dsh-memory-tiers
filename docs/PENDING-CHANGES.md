## 一、记忆星图进核心（已完成 1.3.0）

现在的星图是仓库里的独立工具 `tools/star.mjs`，界面已经满意，**不要改 UI**。要做的是让它成为插件的一部分：

- 整合进核心、能随插件安装（现在不在 npm 包的文件清单里）
- **数据目录必须读配置**里的存储路径，不能写死默认目录
- 能通过插件已有的服务直接打开（配置页入口或命令给链接都行），别另起一个端口
- 顺手考虑：页面现在每 30 秒读一次库，插件内可以直接用已经在内存里的数据

验收：换一个存储目录，星图跟着读新的；能从插件里打开；边写记忆边看，刷新不闪、星点不跳。

## 二、人格槽位（已完成 1.3.0）

要能在「系统提示词之后、记忆块之前」注入一段人格设定，并给别人格插件留接口往里加内容。

- 记忆块必须**始终靠后**——这是硬约束，位置靠注入排序控制，不要改动记忆块自己的内部结构，当然变化更频繁的压缩占位是最后。
- 接口让别人能注册片段、能撤销，拼接结果要确定性（同样的输入每轮拼出同样的文本）
- 人设内容要逐字稳定，不能带时间戳之类每轮变化的东西，否则会破坏缓存
- 开关独立于工作模式
- **分流也要带上人格（可单独开关）**：配置了人格时，送给分流/分类模型的提示词里同样带上，让摘要和分类的口径贴近人格，而不只是影响对话注入（分流提示词在 `core/llm.mjs` 里拼 system 段，从那里挂最省事）。约束：① 只影响「怎么总结」，不要改变三档判定标准本身；② 人格是分流时的临时前缀，不写进摘要正文，也不改已存摘要；③ **这个行为要能单独开关（默认关）**，不要和「注入人格」共用一个开关——注入开人格不代表希望摘要也换口径

验收：看一轮实际请求，顺序是「人格 → 记忆块」；开关人格后没有空白残留；别的人格插件加/减片段后顺序正常；「分流带人格」开关打开后跑一次分流，摘要文风跟着变、但分档结果和条目归属无异常；关掉后摘要恢复原有口径。目前L1是按时间升序排的，这样新东西始终在最后，不会打乱L1缓存。

## 三、工作模式要按会话自治 + 接管黑名单 + 模式提示（已完成 1.3.0）

现在工作模式是全局一个开关，危险点在**忘记关**：

- 某个会话开了工作模式 → 历史保留、不压缩
- 之后关掉（或忘了关又关了）→ 同一个会话变回普通模式，记忆接管压缩会把历史压到 0
- 结果：这个会话在 dsh 里的历史等于被清空（磁盘上还在，但模型看不到了）

所以要：

- **工作模式按会话独立**，不要只全局一个开关
- **接管黑名单**：凡是「开过工作模式、且确实对话过」的会话，即使之后处于非工作模式，这个会话也**不再做历史替代压缩**（保留原有历史）和记忆注入，就相当于仍处于工作模式。名单要落盘、跨重启和升级都不能丢
- **黑名单可以手动删**（误判、或确实想让该会话恢复接管时），但**删除前必须提示风险**：删掉后该会话会恢复记忆接管压缩，历史可能被压到 0。要二次确认，不能一键就删
- **模式提示是给人看的**（不是写给模型的）：界面上要能一眼看出当前会话处于哪种状态——工作模式 / 记忆接管 / 普通，主要是避免把几种模式混用。显眼但不打扰，输入框附近的小标记这类就行，不要弹窗、不要打断对话

验收：会话 A 开工作模式聊几句 → 关掉 → 回到 A 继续说，历史仍在、没有被压成 0；新建会话 B 不受影响；提示标记与实际行为一致；重启后名单仍然生效；在黑名单里删掉某会话时有明确风险提示和二次确认，删完后该会话确实恢复接管。

## 四、工作模式的记忆要「粗」不要「细」（已完成 1.3.0）

工作模式产出多（长回复、工具输出），现在原样进 L1，分流时要么被大批标 `+` 塞进 L2，要么堆成摘要——结果就是 DL2/DL3 被灌满，真正有用的骨架反而被淹没。

要做的是**在进 L1 之前先压一次**：只留骨架——**时间、地点、人物、事件、做了什么**。日志原文、命令输出、过程噪音不用留。

- 压缩放在捕获阶段（进 L1 之前），不要等分流时再处理——那时已经晚了，量大到分不动
- 保留可回溯的东西：时间、涉及的人、关键结论；原文可以按需再查
- 只对工作模式生效，普通模式的记忆质量不受影响
- 成本要可控：优先用规则/截断，必要时才用轻模型，别每条都调

验收：工作模式连跑一段时间，DL2 增长明显变慢，DL3 摘要以「谁在什么时候做了什么」为主；切回普通模式后记忆细度恢复正常。

## 五、保存配置后别再一律要求重载（能热改的尽量热改）（已完成 1.3.0）

现状：配置在插件启动时读一次就好，运行期不再看文件，所以改什么都得手动开关插件一次。

- 完整版的「保存即自动重载插件」做不到——宿主没给插件这种接口
- 但大头可以热改：注入开关、六层容量、抓取上限、整理节奏这些，改成用的时候现读配置（或保存成功后就地替换内存里的配置），保存即生效
- 少数确实要重载的：模型通道、工作模式、定时器间隔。配置页把这些项单独标出来，其余不要再用「需重载」一刀切
- 界面反馈要分清：当场生效的说「已生效」，需要重载的才说「重载后生效」

验收：改 L1 上限 → 保存 → 下一轮整理就按新值走；改注入开关 → 当轮生效；改模型配置 → 明确提示需重载。

## 六、向量存储的规模上限（日志已加，格式改造继续暂缓）

- **已完成**：向量加载失败不再静默——记 `VEC_LOAD_FAIL`（含错误码、文件大小、原因，同一文件只记一次）+ `VEC_ITEM_BAD` 汇总。实测与数据见 `docs/ARCHITECTURE.md` §11.1
- **暂不做**：分片方案（文件名 `deep-part-0000` 预留了位置，但代码只读单文件）
- **真正的天花板**：单文件 base64 JSON 超过约 512MB（约 9.5 万条 × 1024 维）时 `readFileSync` 抛 `ERR_STRING_TOO_LONG`。要扩容优先改存储格式（Float32 直接存二进制，省 33%、可流式读），分片排在它之后
- 现状 504 条 / 2.7MB，距上限约 190 倍，短期无风险
